# Data Model: In-App Notification Center

## New Enumerations

### InAppNotificationSeverity

- `CRITICAL`: Immediate account or access impact.
- `HIGH`: Important security, membership, verification, or irreversible workflow outcome.
- `MEDIUM`: Time-sensitive workflow or communication update.
- `LOW`: Receipt, reminder, recommendation, or informational update.

### InAppNotificationCategory

- `SECURITY`
- `ACCOUNT`
- `APPLICATION`
- `VERIFICATION`
- `SUPPORT`
- `CONNECTION`
- `MESSAGING`
- `MODERATION`
- `SYSTEM`

### InAppNotificationContextType

- `ACCOUNT`
- `MEMBERSHIP`
- `APPLICATION`
- `VERIFICATION_REQUEST`
- `SUPPORT_CASE`
- `CONNECTION_PROPOSAL`
- `CONNECTION`
- `CONVERSATION`
- `MESSAGING_REPORT`

### InAppNotificationKind

The database enum is exhaustive for Feature 016 and mirrors the server event-policy union:

- Account/security: `EMAIL_CHANGED_ALERT`, `PASSWORD_CHANGED`, `RECOVERY_PENDING`, `RECOVERY_CANCELLED`, `RECOVERY_COMPLETED`, `ACCOUNT_SUSPENDED`, `ACCOUNT_REINSTATED`, `ALL_SESSIONS_REVOKED`, `MEMBERSHIP_SUSPENDED`, `MEMBERSHIP_RESTORED`, `MEMBERSHIP_REMOVED`
- Applications: `APPLICATION_SUBMITTED`, `APPLICATION_RECEIVED`, `APPLICATION_STAGE_CHANGED`
- Verification: `VERIFICATION_RECEIVED`, `VERIFICATION_CHANGES_REQUESTED`, `VERIFICATION_APPROVED`, `VERIFICATION_REJECTED`, `VERIFICATION_CANCELLED`, `VERIFICATION_DELAYED`, `VERIFICATION_EXPIRED`
- Support: `SUPPORT_WAITING_FOR_USER`, `SUPPORT_RESOLVED`
- Connections: `CONNECTION_PROPOSAL_CREATED`, `CONNECTION_PROPOSAL_UPDATED`, `CONNECTION_PROPOSAL_INACTIVE`, `CONNECTION_ACCEPTED`, `CONNECTION_REVOKED`
- Messaging/moderation: `MESSAGE_RECEIVED`, `MESSAGE_REPORT_RECEIVED`, `MESSAGE_REPORT_RESOLVED`, `MESSAGE_REPORT_DISMISSED`

## New Entity: InAppNotification

| Field | Type | Rules |
|---|---|---|
| `id` | String | Primary identifier generated by server |
| `recipientUserId` | String | Required relation to `UserAccount`; cascade on account deletion |
| `kind` | InAppNotificationKind | Required allow-listed event kind |
| `category` | InAppNotificationCategory | Required, derived from policy |
| `severity` | InAppNotificationSeverity | Required, derived from policy |
| `title` | String | Required safe localized title, maximum 120 characters |
| `summary` | String | Required safe localized summary, maximum 500 characters |
| `href` | String? | Optional allow-listed internal path, maximum 500 characters |
| `contextType` | InAppNotificationContextType? | Optional; required when `contextId` is present |
| `contextId` | String? | Optional opaque aggregate identifier, maximum 128 characters |
| `deduplicationKey` | String | Unique server-derived identity, maximum 255 characters |
| `correlationId` | String | Sanitized event correlation identity, maximum 128 characters |
| `readAt` | DateTime? | Null means unread; set once through idempotent read mutation |
| `expiresAt` | DateTime | Exactly 90 days after creation for Feature 016 |
| `createdAt` | DateTime | Event-visible creation time |
| `updatedAt` | DateTime | Mutation timestamp |

### Relations

- `UserAccount.inAppNotifications` to `InAppNotification.recipient` is one-to-many.
- No relation to `EmailOutbox` is required. Channels correlate by non-secret business event identity and remain lifecycle-independent.
- Context identifiers are deliberately non-relational because they span several aggregate types and destinations are re-authorized at access time.

### Constraints and Indexes

- Unique `deduplicationKey` prevents duplicate recipient/event records.
- Index `(recipientUserId, createdAt DESC, id DESC)` supports cursor listing.
- Index `(recipientUserId, readAt, expiresAt)` supports unread count and read-all.
- Index `(recipientUserId, contextType, contextId, readAt)` supports context clearing.
- Index `(expiresAt, id)` supports bounded cleanup.
- Check constraints enforce title/summary/href/context/deduplication/correlation lengths and paired context fields.

## Existing Entity Changes

### UserAccount

Add `inAppNotifications` relation. No session, role, identity, or email fields change.

### AccountPreferences

Feature 016 does not add a broad master switch. Mandatory critical/high notifications cannot be disabled. Existing email booleans remain unchanged. Optional in-app category switches are deferred until a concrete optional category is exposed; event policy defaults specified in Feature 016 remain deterministic.

### ProfessionalConnectionNotification

No schema removal. Existing unexpired records are copied to `InAppNotification` using `connection-legacy:<deduplicationKey>`, preserving `createdAt`, `readAt`, and `deleteAfter` capped to the 90-day policy. New producers stop writing this table after migration.

### RecruitmentNotificationWork

No schema removal. Existing pending/retryable rows are converted idempotently. Candidate targets become one notification; company targets fan out to currently active authorized memberships. A row becomes `SENT` only after all intended unified rows exist. New application producers create unified rows directly and no longer create new recruitment work.

## State Transitions

### Notification Read State

```text
UNREAD (readAt = null) -> READ (readAt = timestamp)
READ -> READ (idempotent, original readAt preserved)
```

Feature 016 does not expose a mark-unread transition.

### Visibility Lifecycle

```text
CREATED -> VISIBLE -> READ (optional) -> EXPIRED -> DELETED
```

Expiration never deletes originating audit, email outbox, message, application, report, support, verification, or connection records.

## Validation Rules

- Only event-policy output may be persisted.
- `title` and `summary` are plain text; HTML is rejected.
- `href` must begin with one approved internal route prefix and must not contain credentials or token-like query parameters.
- `contextType` and `contextId` must both be null or both be present.
- `deduplicationKey` includes recipient identity and logical event identity.
- Untrusted names and text are normalized, bounded, and rendered as text.
- Client input never supplies notification kind, title, summary, recipient, severity, expiry, or deduplication identity.
- Read endpoints accept only IDs/context references and always scope mutations to the authenticated user.

## Migration and Rollback

1. Create enums, table, constraints, indexes, and user relation.
2. Backfill legacy connection rows with `ON CONFLICT DO NOTHING`.
3. Run application-level recruitment work bridge for recipient resolution.
4. Verify source-to-target counts and sampled read-state parity.
5. Deploy producer switch and unified read APIs/UI.
6. Rollback application code by returning to legacy producers; unified table remains additive and harmless.
7. Defer old-table removal to a separately reviewed migration after one stable release.
