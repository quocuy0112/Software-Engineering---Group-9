# Data Model: Identity, Authentication, and Account Recovery

PostgreSQL is the only production database; Prisma and Prisma Migrate own data access and migrations. Better Auth-owned tables appear once below. Names describe responsibilities even if pinned Better Auth physical model names remain lowercase/default for adapter compatibility.

## Enums

- `AccountState`: `PENDING_VERIFICATION`, `ACTIVE`, `SUSPENDED`, `DELETED`
- `TokenPurpose`: `VERIFY_EMAIL`, `RESET_PASSWORD`
- `TokenStatus`: `ACTIVE`, `CONSUMED`, `SUPERSEDED`, `EXPIRED`
- `ChallengePurpose`: `PASSWORD_LOGIN_2FA`, `RECENT_AUTH`
- `AuditResult`: `SUCCESS`, `FAILURE`, `DENIED`
- `EmailKind`: `VERIFY_EMAIL`, `RESET_PASSWORD`, `PASSWORD_CHANGED`, `SECURITY_ALERT`
- `OutboxStatus`: `PENDING`, `PROCESSING`, `SENT`, `RETRYABLE`, `DEAD`

## Better Auth-Owned Models

### UserAccount (`user`)

The Better Auth user row is also the SmartHire domain user root; `UserAccount` is the documentation/domain name.

| Field | Rule |
|---|---|
| `id` | immutable string primary key |
| `name` | validated Unicode, 1–120 characters |
| `email` | canonical display email |
| `normalizedEmail` | trimmed/case-normalized email, unique and required |
| `emailVerified` | Better Auth field; state policy remains authoritative |
| `state` | required, default `PENDING_VERIFICATION` |
| `twoFactorEnabled` | Better Auth plugin field, default false |
| `stateChangedAt` | required timestamp |
| `deletedAt` | nullable; required only for `DELETED` |
| Better Auth timestamps | preserve pinned schema |

Constraints/indexes: unique `normalizedEmail`; check `state = DELETED` iff `deletedAt IS NOT NULL`; index `(state, id)` for authentication cleanup. Every normal user has exactly one base Candidate identity. This feature enforces states during authentication; administrator suspension/reinstatement/deletion commands are future User Management scope.

### AuthProviderAccount (`account`)

Better Auth credential/provider account. Preserve all pinned `1.6.11` adapter fields and unique provider/account identity. Only the credential provider is configured; no Google or social provider. Password hashes remain Better Auth-owned. FK to `UserAccount` uses the pinned adapter relationship and safe deletion policy.

### Session (`session`)

Better Auth is authoritative and its schema is not duplicated.

| Field | Ownership/rule |
|---|---|
| `id`, `token`, `userId`, `expiresAt`, `createdAt`, `updatedAt`, `ipAddress`, `userAgent` | Preserve Better Auth 1.6.11 Prisma schema. `token` is the opaque browser credential and is unique; do not rename/hash it as `tokenDigest`. |
| `lastActivityAt` | SmartHire additional session field, server-controlled, indexed; supports the 30-minute idle limit. |
| `absoluteExpiresAt` | SmartHire additional field fixed at creation + 7 days, indexed; never extended by refresh. |
| `revokedAt`, `revocationReason` | Optional SmartHire audit/cleanup extensions if pinned hooks preserve revoked rows; otherwise deletion plus `AuditEvent` records revocation. |

FK `userId → UserAccount.id`; index `(userId, expiresAt)`, `(userId, lastActivityAt)`, `(absoluteExpiresAt)`. Server validation rejects when Better Auth validation fails, idle age exceeds 30 minutes, absolute expiry passes, or state is not Active. Session creation is serialized per user and evicts least-recent non-current sessions until at most five remain.

### Verification (`verification`)

Preserve the Better Auth table only for Better Auth-owned verification purposes. Do not force SmartHire recovery tokens into it unless version-locked tests prove its identifier/value/expiry semantics and transaction needs match. It is not a session or challenge.

### TwoFactor (`twoFactor`)

Preserve the pinned two-factor plugin schema: one row per `UserAccount` with TOTP secret, serialized backup codes, verified state, failed-verification count, and lock timestamp as generated by Better Auth `1.6.11`. Unique `userId`, FK to user with reviewed deletion behavior.

Better Auth is the sole owner of TOTP and backup-code generation, persistence, regeneration, and single-use consumption. No SmartHire `BackupCodeSet` or `BackupCode` table exists, and the base SmartHire `TokenProtector` does not encrypt/decrypt TOTP secrets. Before implementation proceeds, compatibility tests must prove required protection at rest and atomic concurrent consumption. A TOTP persistence-encryption extension is allowed only when the pinned spike proves it necessary, Better Auth integration supports it safely, and an approved ADR documents the extension while preserving Better Auth ownership.

## SmartHire-Owned Models

### CandidateIdentity

`userId` primary key/FK to `UserAccount`; base Candidate identity fields only. Restrict destructive physical deletion until retention/deletion policy runs; a Deleted user is soft-deleted for authorization.

### SecurityToken

Purpose-specific email verification and password reset token record.

| Field | Rule |
|---|---|
| `id` | primary key |
| `userId` | FK to `UserAccount` |
| `purpose`, `status` | required enums |
| `tokenDigest` | unique keyed digest; plaintext returned only for the email intent |
| `expiresAt` | required, indexed |
| `consumedAt` | nullable; set once with `CONSUMED` |
| `supersededAt` | nullable |
| `createdAt`, `createdByRequestId` | required |

Use a partial unique constraint for at most one `ACTIVE` row per `(userId,purpose)`. Consumption is a conditional update requiring Active, unexpired, and unconsumed state; concurrent consumption succeeds once. Retain used metadata for audit/anti-abuse, never token plaintext.

### AuthenticationChallenge

Temporary pre-authentication/security state, not a full session and never accepted for protected resources: `id`, unique `handleDigest`, `userId`, `purpose`, `expiresAt` (five minutes for login 2FA), `attemptCount`, `maxAttempts`, `consumedAt`, `createdAt`, and bounded context digests. FK to user; indexes on `(handleDigest, expiresAt)` and `(userId, expiresAt)`. Delete/expire after use. It does not own TOTP or backup codes.

### EmailOutbox

`id`, `kind`, nullable `userId`, nullable `securityTokenId`, recipient reference/encrypted value, `templateVersion`, allowlisted payload reference, unique `idempotencyKey`, status, attempts, lease owner/expiry, `nextAttemptAt`, provider message ID, safe error code, timestamps. Index `(status,nextAttemptAt)`. FK deletion uses SetNull only where immutable delivery history must remain; never store full token URLs in logs/errors.

### AuditEvent

Append-only: `id`, `occurredAt`, actor type, nullable `actorUserId`, nullable `actorSessionId`, action, target type/id, result, correlation ID, keyed IP-prefix digest, user-agent family, schema-validated context. Index actor/time, target/time, action/time, and correlation ID. The application database role has no update/delete permission. Foreign references are logical/nullable so account cleanup cannot erase audit history.

### RateLimitBucket

`scope`, `subjectDigest`, `windowStart`, `count`, `blockedUntil`, `updatedAt`; composite PK `(scope,subjectDigest,windowStart)` and index `blockedUntil`. Persist only limits requiring cross-instance consistency. Digests prevent storing raw email/IP keys.

## State Transitions

| From | To | Trigger owned here |
|---|---|---|
| none | Pending Verification | successful registration |
| Pending Verification | Active | one-time email-verification token consumption |

Pending/Active → Suspended, Suspended → Active, and any state → Deleted commands belong to future User Management. This feature consumes those states: only Active may authenticate; Suspended/Deleted sessions are rejected/revoked; Pending Verification may only access verification/resend behavior.

## Transaction and Concurrency Boundaries

1. Registration: unique normalized email + `UserAccount` + `AuthProviderAccount` + Candidate identity + verification `SecurityToken` + audit + outbox.
2. Verification: conditional token consume + state transition + audit.
3. Resend/reset request: supersede prior active token + create replacement + outbox + audit, with generic response.
4. Password reset: conditional token consume + credential update + all-session/challenge revocation + sibling-token supersession + audit + notification. If Better Auth cannot join the Prisma transaction, use an explicit idempotent orchestration/retry state and fail closed.
5. Session admission: serialize per user, create Better Auth session, enforce absolute/idle fields and five-session cap, audit.
6. Backup-code use: Better Auth plugin operation must be proven atomic under concurrent PostgreSQL submissions.
7. Outbox claim/send: `FOR UPDATE SKIP LOCKED` or equivalent lease; idempotency key prevents duplicate logical sends.

## Deletion Safety and Integrity Review

- Soft-deleted `UserAccount` rows remain unavailable to authentication and preserve required audit/legal links.
- Cascade only ephemeral challenges and tokens when policy permits; restrict or null durable audit/outbox references.
- Required uniques: normalized email, Better Auth provider/account identity, Better Auth session token, challenge handle digest, security-token digest, outbox idempotency key.
- Required foreign keys and indexes are listed above; migration SQL must add PostgreSQL partial uniques/checks not expressible in Prisma.
- Scheduled cleanup handles expired sessions, tokens, and challenges but never substitutes for request-time validation.
